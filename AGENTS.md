# AGENTS.md – ReemGame

Shared rules for every tool on this project. `CLAUDE.md` only points here: change the rules in this file.

You are building a 2D point-and-click adventure game for Muslim Arab children, in Godot with the Popochiu plugin. The MVP (Grandpa's farm and the flower meadow) is built; the full game is described in `docs/ROADMAP.md`. The user is a beginner in Godot: explain what you did in plain words, and tell them exactly what to click when they need to check something.

**Follow `docs/PIPELINE.md` and `docs/ROADMAP.md`.** PIPELINE.md says who does what and how the queues in `content/` work. ROADMAP.md says what to build and in which order.

## Roles

* **Claude Code and Codex are both builders, with the same role and the same rules** (everything in this file applies to both). They write the station specs, fill the queues, and build the game in Godot.
* **Images: only Codex.** Codex can also generate the images in `content/art_queue.md`; Claude Code cannot, so it only writes the rows.
* **Voices: Codex or Claude Desktop** (with ElevenLabs) generates voices, dialogue and words from the queues. Codex can do everything: build, identify objects, generate images and voices. Claude Code builds, identifies objects and writes queue rows, but cannot generate images or voices.
* **Whoever is working continues exactly where the other stopped**, using the Handoff at the top of `PROGRESS.md`: finish the half-done step it describes before starting anything new, and follow the same plan and naming.

## How the tools take turns

* Claude Code, Codex and Claude Desktop work **in turns, in this same local folder** (`C:\Users\ACER\Desktop\Games\reem-game`). Only one tool works at a time.
* **This local folder is the source of truth. GitHub is only a backup.** Do not pull between turns.
* Work only on the `main` branch. Do not create other branches.

**At the start of a session:**
1. Run `git status`. If there are uncommitted files from the previous tool (for example new audio from Claude Desktop, which cannot use git), check they match a queue row and commit them first with a message naming that tool.
2. Read `AGENTS.md` (this file), `docs/PIPELINE.md`, `docs/ROADMAP.md`, `game_spec.md` and `PROGRESS.md`, starting with the Handoff section at the top of `PROGRESS.md`. Then continue from the Handoff's "What is next" and "Half-finished" points.

**At the end of a session:**
1. Run the checks (see "Checks" below) and fix every error you caused.
2. Update the **Handoff** section at the top of `PROGRESS.md`: who worked (Claude Code, Codex or Claude Desktop), the date, the branch, what was done, what is next, and anything half-finished, with enough detail (files, functions, the next concrete step) that the other builder can continue exactly from there. Add any choice you made on your own under **Decisions to review**.
3. Commit with a clear message, then push to GitHub as a backup (`git push origin main`). If the push fails (no network), the commit is enough: say so in the Handoff.

**Never leave work uncommitted.** If you must stop in the middle (usage limit, error you cannot fix), commit what you have, say in the Handoff exactly where you stopped and what is broken, and push.

## Sources of truth

* `docs/ROADMAP.md` and `docs/PIPELINE.md`: the full game and the way content is made. Change them only when the user asks.
* `game_spec.md`: what to build, room by room. Follow it exactly. The builder writes each new station into it before anything is drawn (see PIPELINE.md). If something in it is impossible or unclear, choose the most reasonable option, note it under "Decisions to review" in `PROGRESS.md`, and continue.
* `game_data/lines.json`: every dialogue line (Arabic text + audio path), keyed by line ID. Never retype or change the Arabic text of an existing line. New lines are added here and to `content/voice_queue.md` at the same time.
* `game_data/words.json`: the word-discovery words. Generated by `tools/make_words.py`: to add or change a word, edit the table in that script and run `python tools/make_words.py` from the project folder. It also adds each new word to `content/word_queue.md` (never changing existing rows). Never edit `words.json` by hand. `game_data/word_areas.json` (where each word is on screen) is edited by hand.
* `content/art_queue.md`, `content/voice_queue.md`, `content/word_queue.md`: the queues of images, lines and words still to make, each with a Status column (`todo`, `done`, `problem: <reason>`). Never delete rows; change their status.
* `PROGRESS.md`: the Handoff, decisions to review, what is done, what the user confirmed, known problems, and the test checklist.

## Originals and new files

* **Originals are never edited:** never edit, move, rename or delete anything that already exists in `res://assets/` (art, audio, fonts). Put cut pieces and anything generated from them in `res://assets/cut/` or under `res://game/`.
* **New files listed in the queues may be added:** Codex adds the images in `content/art_queue.md` and Codex or Claude Desktop adds the audio in `content/voice_queue.md` and `content/word_queue.md`, at exactly the path and name in the queue. Once added, they are originals too.
* If a missing image or sound blocks a station, use a clearly marked placeholder under `res://game/` (never in `res://assets/`) and keep building.

## ElevenLabs credentials

- Never write the ElevenLabs API key in any repo file: code, documentation, examples, queues, logs or Godot resources. Use connected authentication or `ELEVENLABS_API_KEY` supplied through the process environment; keep credentials outside this project.
- `.gitignore` excludes local environment files, credential/config paths and generation logs. Ignore rules match paths, not contents: if a tool creates any other file containing a key, remove the credential and ignore that exact path before staging. Never force-add secrets.
- Inspect staged changes for credentials without printing secret values before every commit. Ignore rules do not protect tracked files: remove credentials before committing. If a real key was already committed, report it and rotate it; ignoring does not remove history.

## Popochiu rules

* Popochiu 2.0.3 is in `res://addons/popochiu/`. **Before writing Popochiu code, read its source and its example templates in `res://addons/popochiu/` to confirm class names, method names and signals. Do not guess the API.**
* Popochiu was not officially tested on Godot 4.7: if something in it breaks, say so plainly and propose the smallest fix.
* Godot scene (`.tscn`) and resource (`.tres`) files are text, but prefer creating Popochiu rooms, characters, props, hotspots and inventory items the way Popochiu expects (its own templates and folder layout under `res://game/`). If you must write `.tscn` files by hand, keep them minimal and valid.

## Arabic rules

* Arabic text must display **connected and right to left**, in dialogue, choice buttons and the word bubble, with the font in `res://assets/fonts/` (Cairo).
* Copy Arabic text from `game_data/lines.json` or `game_data/words.json`; never retype it, and keep every diacritic.
* Word-discovery words have full diacritics and no tanween (pausal form, for example شَجَرَة, بَاب).
* New dialogue: simple Modern Standard Arabic with full diacritics and Islamic manners (greetings, بسم الله، إن شاء الله، جزاك الله خيراً، الحمد لله). Any Quran or hadith quote must be exact and attributed, and only from Grandpa. If you are not certain of a quote's exact wording, do not use it: note it under "Decisions to review".
* If Arabic shows as boxes or separate letters, stop and say so: do not work around it by changing the text.

## Child-friendly rules

* No game over, no timers, no scary effects.
* Every click does something or nothing; it never breaks the game or leaves the player stuck.
* Choices follow the choice design rules in `docs/ROADMAP.md`: a kind option and a tempting wrong option; the wrong one wilts a branch of the heart tree and can always be repaired. Characters stay gentle, never shaming; the lesson shows in the result, not in a sermon.

## Working rules

1. **One room or feature at a time**, in the build order of `docs/ROADMAP.md` (section 5). After finishing one, run the checks, commit, write in `PROGRESS.md` how the user can test it (which key to press, what they should see and hear), and move on.
2. **Don't ask the user during building:** choose the most reasonable option, note it under "Decisions to review" in `PROGRESS.md`, and continue. Bug fixing and polishing happen at the end. Never wait for the other tools: build with whatever art and audio exist.
3. **Small, safe steps:** commit after each finished piece of work with a clear message.
4. **Visual positions are starting points:** the user adjusts them. Make positions easy to change (exported variables, clearly named nodes, or the fraction-of-screen JSON files).
5. **Keep `PROGRESS.md` up to date:** besides the Handoff and Decisions to review, record what the user confirmed and known problems.
6. **Close Godot before editing:** the user should close the Godot editor while a tool changes files, and reopen it to test. Godot open at the same time can overwrite changes.

## Checks

Run every check from the project folder. Any `ERROR` or `SCRIPT ERROR` in the output is a bug, except the usual "leaked at exit" / "resources still in use at exit" lines and "Aseprite command failed" during import (Popochiu's Aseprite importer, not used by this game). The playtest prints lines starting with `[PLAYTEST]`: every line should say `ok`, and the last line `DONE`.

The automatic playtest (`tools/playtest.gd`) has four paths: `green`, `sand`, `mixed` (the three story playthroughs) and `words` (word discovery with real mouse presses). Run all four.
